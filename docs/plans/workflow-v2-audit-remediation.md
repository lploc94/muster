## Target

## Invariants
- Only an open top-level root coordinator outside a workflow activation may call `define_workflow` or either form of `start_workflow`; capability projection and execution-time authorization must both enforce the boundary.
- A workflow activation can execute its frozen node contract, publish NEXT/PREV/FAIL, and use ordinary child-task delegation when its task profile grants it, but can never define, start, invoke, or dynamically add a workflow.
- Every agent node has a declared outcome with `requireExplicitDisposition:true` and a bounded FAIL route, so the existing `workflow_fail` MCP tool is always available and authorized against frozen activation authority. A valid FAIL closes the run immediately through `agent_fail`; no agent workflow turn uses implicit NEXT.
- `WorkflowPolicy.failWorkflow` is always literal `true`; a definition, snapshot, or composite component carrying `false` is invalid because Workflow V2 has no continue-after-required-node-failure policy.
- A normal `end_turn` carrying text without a valid disposition is protocol evidence, never a semantic success/failure heuristic. It enters the existing activation-owned decision repair for at most three completed attempts; attempt-three exhaustion closes the run with `decision_missing`/`decision_invalid`, while turn budgets or the run deadline may close it earlier. Reload, replay, or repeated refusal cannot create an unbounded correction loop.
- A typed ACP `stopReason:'refusal'` is machine evidence, not prose: on a workflow agent activation with no already accepted disposition it atomically fails the turn/run as `agent_fail` on that attempt, suppresses generic retry/runtime fallback, and queues no decision correction. A valid disposition claim that raced first remains authoritative. Ordinary tasks and non-refusal transport/provider errors retain their existing failure/recovery behavior.
- Every terminal workflow failure owns one immutable bounded `WorkflowFailureDetail`: safe semantic component/node key and optional title when a node is responsible, closed source/code, exact UTF-8-bounded model report when available, a truncation flag, and decision attempts when applicable. Explicit `workflow_fail` contributes its required `reason`; typed refusal contributes the final assistant text emitted before the refusal signal; decision exhaustion contributes the latest nonempty assistant response. Missing text receives a fixed host explanation. The owning coordinator receives this detail in `start_wait` terminal delivery and same-root inspection, and the user sees it in the run UI; model text is clearly framed/rendered as untrusted data and never grants authority.
- `start_workflow` retains its existing reusable-definition form and durable wait/resume behavior. Sequential independent starts continue to bind `{ name, fromRun, output }`; removing nested runs must not remove `start_wait` continuation recovery.
- Every canonical definition assigns one unique semantic output name and kind to every node. Terminal outputs remain completion outputs; nonterminal outputs are stable checkpoints. Neither kind exposes a physical node, task, turn, gate, artifact, or revision as caller authority.
- A composite is a closed start request, not a definition: it uses immutable versioned workflow refs plus optional inline one-node canonical manifests, connects public component interfaces, maps all external inputs and node outputs explicitly, flattens once before execution, and never writes `workflow_definitions` rows.
- Every ordinary or composite run executes only its immutable run-owned snapshot. Reusable definitions are source products/provenance and cannot be consulted as live execution authority after start.
- A result is reusable only after its containing run is terminal and only when an exact immutable `next_result` artifact has valid workflow-node provenance from a successfully settled producer turn. Terminal `succeeded`, `failed` (including timeout), and `cancelled` runs are eligible because terminalization freezes further revisions and later reuse is an explicit same-root decision; live runs are not, because a later PREV revision could supersede the apparent result.
- Explicit reuse never changes the source run or node history, hides failures, fabricates aggregate success, queues a producer turn, retries work, or chooses a downstream workflow. It pins the latest valid committed revision selected by semantic output name and exact kind inside the consumer-start transaction.
- Safe author-level identities, semantic contracts, topology, titles, input refs, and package-relative references may be projected when an audience needs them. Credentials, actual secrets, absolute host paths, SQL rows, unbounded diagnostics, and raw physical authority never cross public boundaries; prompt/script/artifact bodies remain only on existing bounded execution, transcript, terminal-delivery, and exact reuse paths.
- All parsing, expansion, fingerprints, projections, and persistence remain bounded, deterministic, closed to unknown fields, replay-safe, fail-closed on corruption, and covered by the existing no-fan-out/acyclic/resource policies.
- The schema cutover is reset-only. Schema 7 fails closed and requires explicit reset; no migration, dual schema, compatibility decoder, or fallback to superseded definition/nested-run rows is added.
- Obsolete schema-7 `child_return` state is not a supported history surface. While the current schema-7 store is still openable, the cleanup boundary may use one narrow legacy-state reader (not an execution/recovery reader) to purge it; after the Phase 4 schema-8 cutover, old stores fail closed and this is not a migration path. The purge removes only rows owned by that retired activation and its retry lineage; shared workspace, ordinary delegated-task, and canonical active workflow rows are never purged. It is idempotent, aborts without partial changes when ownership or integrity is ambiguous, and runs before a schema-7 terminal-run guard is evaluated.

## Phase 2: Fail Closed on Agent Refusal or Missing Outcomes
- Status: complete
- Depends on: Phase 1
- Goal: Give every agent workflow node an explicit machine-level failure path and guarantee that text-only refusal or any other missing outcome terminates through a bounded durable path that tells the owning coordinator and user which node failed and what it reported, rather than producing implicit success, an opaque code, or an unbounded loop.
- Current behavior: `WorkflowNodeSpec.outcome` and its FAIL route are optional, `decodeAgentOutcome` accepts `requireExplicitDisposition:false`, `capabilitiesFor` exposes `workflow_fail` only when no frozen outcome or a declared fail route permits it, and `engine.ts` converts a clean optional text-only completion into implicit NEXT.
